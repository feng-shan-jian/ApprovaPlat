本任务处理 2026-08-16 工作流架构重构的最终审查缺口。目标是把当前“多数功能和测试已完成，但架构与验收未完全闭合”的状态收敛为可真实开发、可真实运行、可真实验收的最终实现。

## 2. 执行原则

1. 以当前确认的前端功能、后端业务契约和 Flowable 正式能力为边界，修复架构缺口，不扩展新的业务功能。
2. 开发库允许直接删除、重建和覆盖。数据库结构以最终基线为准，不为开发数据编写迁移、回填、兼容和回滚逻辑。
3. 旧代码调用完成迁移后直接删除旧类、旧接口、旧 Mapper、旧 SQL、旧测试和旧文档，不保留转发门面。
4. 仓库内数据库 dump、测试夹具数据、运行日志、临时截图、旧制品副本和过期任务证据直接删除，不进入 Git 历史。
5. 持久化数据必须存在明确的页面、API、后台任务或合规消费者，并具备明确的生命周期。没有消费者的数据不新增表。
6. 校验集中在请求参数、权限、业务状态、并发版本、租约所有权和外部系统边界。已由类型、数据库约束或上游契约保证的条件不重复堆叠校验。
7. 优先删除无效代码，其次合并重复逻辑、简化控制流、拆分职责，最后才使用设计模式。设计模式只用于已有多实现变化点，本次仅通知渠道适合 Strategy。
8. 新增或修改关键函数按照根目录 `AGENTS.md` 补充中文块注释、入参返回说明、关键变量含义和关键状态流说明。

## 5. 数据生命周期最终设计

### 5.1 统一原则

`WorkflowDataRetentionCoordinator` 保留为统一调度入口，各领域拥有自己的资格查询和批量删除方法。协调器只负责编排、批次控制、指标和错误隔离。

清理采用有界批次和稳定主键顺序。多个节点同时执行时依靠状态条件、主键条件和数据库行锁保证幂等，不增加全局锁和清理状态表。

未完成业务数据、未读数据、待投递数据和未解决死信不自动删除。

### 5.2 最终保留矩阵

| 数据 | 删除条件 | 默认保留期 | 删除关系 |
| --- | --- | ---: | --- |
| `wf_notification_outbox` | `PROCESSED` 或 `CANCELLED` | 90 天 | 删除前确认不存在需要保留的业务关联；`PENDING`、`RETRYING`、`DELIVERING`、`DEAD_LETTER` 保留 |
| `wf_notification_inbox` | 已读 | 180 天 | 未读保留 |
| `wf_runtime_event_request` | 已完成终态 | 90 天 | 待处理和失败待补偿记录保留 |
| `wf_process_draft` | `SUBMITTED` 或 `DELETED` | 30 天 | 编辑中草稿保留 |
| `wf_collaboration_message` | `PROCESSED` | 90 天 | 同事务先删除对应 `INBOUND` 审计；死信保留 |
| `wf_collaboration_outbox` | `PROCESSED` 或 `CANCELLED` | 90 天 | 同事务先删除对应 `OUTBOUND` 审计；死信保留 |
| `wf_collaboration_message_audit` | 随入站或出站父记录删除 | 与父记录一致 | 不作为独立清理域，不允许形成孤立记录 |
| `wf_attachment` | 对象存储已物理删除 | 90 天 | 租约中和待重试记录保留 |
| `wf_bpmn_event_audit` | 流程实例已结束 | 180 天 | 按 `create_time,audit_id` 批量删除 |
| `wf_task_sla_execution` | `COMPLETED` 或 `ESCALATED` | 180 天 | 删除执行记录时同步删除 SLA audit |
| `wf_task_sla_audit` | 随 SLA execution 删除 | 与父记录一致 | 将外键改为 `ON DELETE CASCADE`，不独立残留 |
| `wf_copy` | 已读或逻辑删除，且流程已结束 | 180 天 | 未读且有效记录保留 |
| `wf_controlled_loop_execution` | 流程实例已结束 | 180 天 | 按 `create_time,execution_id` 批量删除 |

保留期进入 `WorkflowDataRetentionProperties`，提供明确默认值和正整数配置校验。配置只表达保留天数、批次大小和调度周期，不增加每张表的启停开关。

### 5.3 协作审计一致性

`wf_collaboration_message_audit.message_id` 同时指向入站和出站两种父表，无法建立单一外键。保留现有 `message_id + direction` 模型，并将删除动作放入父记录清理事务：

1. 按父记录主键领取满足条件的有界批次。
2. 按 `message_id` 和 `direction` 删除审计。
3. 删除对应父记录。
4. 事务提交后记录删除数量指标。

集成测试必须证明父记录删除后审计为零，保留父记录时审计不被提前删除。

### 6.3 outbox 事务边界

外部网络请求不得运行在数据库事务或行锁内部。固定流程如下：

```text
短事务 claimNext
  -> 状态改为 DELIVERING
  -> 写入 lease_owner、lease_expires_at、revision
  -> 提交并释放连接和行锁

事务外 channel.deliver
  -> SMTP / SMS / 站内信适配
  -> 生成脱敏、稳定的 DeliveryResult

短事务 completeDelivery
  -> 按 outbox_id + DELIVERING + lease_owner + revision 条件更新
  -> 成功进入 PROCESSED
  -> 可重试失败进入 RETRYING
  -> 永久失败或次数耗尽进入 DEAD_LETTER
  -> 清空租约并提交
```

`WorkflowNotificationOutboxService.deliver()` 当前在 `REQUIRES_NEW` 事务内调用渠道，必须删除或改造成无事务协调方法。数据库状态提交继续使用条件更新，不通过持锁等待网络结果。

站内信写入使用业务唯一键保证幂等。站内信写入成功但 outbox 完成更新失败时，下次重试命中同一唯一键并继续完成 outbox，不产生重复收件箱记录。

### 6.4 状态规则

允许的主要迁移：

```text
PENDING -> DELIVERING
RETRYING -> DELIVERING
DELIVERING -> PROCESSED
DELIVERING -> RETRYING
DELIVERING -> DEAD_LETTER
PENDING/RETRYING/DELIVERING -> CANCELLED
DEAD_LETTER -> RETRYING
```

所有写入使用状态、租约持有者和 revision 条件。状态冲突返回稳定的业务冲突，不吞掉异常，不返回伪成功。
