# 工作流发布与回滚

## 发布资产

每个发布包必须冻结：

- `ruoyi-admin.jar` 和完整前端静态文件
- `sql` 中本版本需要的正式 SQL 与验收脚本
- `deployment` 配置、systemd、Nginx、门禁和门禁测试
- `RELEASE-METADATA`、完整 `SHA256SUMS` 和 `sql/release-order.txt`

发布目录必须不可变、无符号链接、无硬链接复用，并由外部批准的 Git commit 和清单 SHA-256 锚定。

## 首个正式版本

当前 `release-order.txt` 固定包含数据库基线的七个工作流 SQL 文件，只能在空 schema 上执行。首发使用 `fresh-install` 门禁，`previous_release_id=NONE`；不能伪造上一版本，也不能在非空数据库重放基础建表脚本。

## 后续版本

第二个正式版本开始，发布清单只包含从上一正式数据库版本到当前版本所需的新迁移。迁移遵循先扩展后收缩：先增加向前兼容结构，再发布使用新结构的应用；删除、重命名、缩窄类型或改变字段语义必须拆分到旧版本退出支持之后。

发布数据库账号常态锁定，只在受控窗口短时解锁。执行失败、信号中断或终端退出时必须先重新锁定账号，再保留原失败结果。

## 发布流程

1. 固定发布 ID、Git commit、构建时间和资产哈希。
2. 执行 `deployment/scripts/tests/workflow-release-gate-test.sh`，确认门禁自身没有被削弱。
3. 使用 `workflow-release-gate.sh preflight` 校验发布包、配置、SQL 顺序和批准锚点。
4. 完成数据库与附件一致性备份，并验证备份可恢复。
5. 摘除流量，执行本版本批准的数据库步骤，运行三组只读验收。
6. 原子切换 JAR、前端和配置，启动后端并采集 readiness 与指标。
7. 使用真实职责账号执行登录、查询、发起、办理、拒绝权限和附件烟测。
8. 达到批准条件后逐步放量，并进入 24/72 小时观察。

## 应用回滚

- 回滚只切换到已经冻结且与当前数据库兼容的上一应用版本。
- 不执行反向 DDL，不修改历史发布包，也不向旧包补入当前版本文件。
- 回滚后必须重新验证健康、核心读写、实例历史、审计和附件一致性。
- 如果数据库变化无法保证上一应用版本兼容，则该发布不能进入生产窗口。

## 证据规则

门禁 profile 包括 `fresh-install`、`rehearsal`、`production`、`production-24h` 和 `production-72h`。后四类在适用时必须绑定真实上一版本；生产 profile 还必须绑定两次独立彩排证据。

证据只能保存状态、摘要、哈希、时间和受控标识。密码、Token、Cookie、环境文件正文、客户端配置正文和业务敏感响应不得进入证据目录或 Git。
