# 项目澄清记录

本文档记录 ApprovaPlat 项目在功能定位、业务契约、技术实现和交付标准上的正式澄清结论。每个结论一经确认，即作为后续代码、数据库脚本、测试、部署配置和项目文档清理的依据。

## CLAR-001 当前工作区是正式功能基线

- 状态：已确认
- 确认日期：2026-08-07
- 原始问题：当前未提交的新审批功能与 Git HEAD、旧版说明及旧发布基线存在范围差异，应以哪个状态作为项目真实目标？
- 正式结论：以当前工作区包含的全部新审批功能作为正式目标基线。即使这些功能尚未提交，也应先提交并继续保留，不得按 Git HEAD 所代表的旧版功能范围回退或删除。
- 适用范围：连接器、DMN、运行事件、扩展注册表、设计器增强、表单扩展及其前后端接口、数据库结构、权限、测试和部署能力。
- 清理影响：与当前工作区新功能冲突或仍描述旧版功能边界的 README、生产文档、数据库迁移顺序、发布门禁和验收基线均属于待更新对象；新功能本身不因旧文档未同步而被视为冗余或过期实现。
- 保持不变：已经确认并通过测试的审批业务行为、权限边界、数据持久化和接口契约，在后续澄清明确要求变更前保持稳定。

## CLAR-002 项目以生产级企业审批平台为主定位

- 状态：已确认
- 确认日期：2026-08-07
- 原始问题：ApprovaPlat 应定位为可直接生产部署的企业审批平台，还是仅用于技术选型、教学或演示的参考实现？
- 正式结论：ApprovaPlat 的主定位是可真实生产部署的企业审批平台。项目可以为 Flowable 8 技术选型和落地提供参考，但“参考实现”只是附加价值，不能作为降低生产功能完整度、数据一致性、安全性、可运维性或发布验收标准的理由。
- 适用范围：产品介绍、功能范围、架构设计、实现质量、测试策略、部署方案、发布门禁、运维手册和验收结论。
- 清理影响：README 及其他文档中容易让人理解为演示项目、样例工程或非生产实现的描述应删除或改写；所有对外功能必须遵循真实前后端、正式数据结构、权限和状态闭环要求。
- 保持不变：项目仍可明确说明其对 Flowable 8 工程化落地具有参考价值，但不得弱化“生产级企业审批平台”的主定位。

## CLAR-003 当前结构候选为首个正式数据库基线

- 状态：已确认，结构审查已完成
- 确认日期：2026-08-07
- 原始问题：是否存在必须从旧结构无损升级的真实已部署数据库，还是可以将当前结构作为首个正式数据库基线？
- 正式结论：目前不存在需要兼容的真实已部署环境。当前数据库结构在完成冗余、命名、约束、职责和语义冲突审查，并清除由本地开发历史造成的误解后，可以作为首个正式数据库基线。
- 适用范围：工作流业务表、Flowable 官方表、菜单与权限初始化、校验 SQL、安装顺序、发布门禁、备份恢复和数据库文档。
- 清理影响：不得仅为兼容未正式发布的本地开发结构而永久保留 `.1`～`.14` 增量迁移、旧表数量或旧发布顺序；确认当前完整基线覆盖全部必要结构后，应合并开发期迁移并建立新的正式版本起点。
- 保持不变：未来从首个正式基线开始产生的版本必须使用不可篡改、顺序明确、可验证且可回滚的增量迁移，不得继续改写已经发布的正式基线。
- 当前审查证据：完整业务基线已包含 44 张唯一的 `wf_*` 表，其中条件分支、动态参与者、子流程、申请草稿、自动抄送、普通审批通知、受控循环、多池协作、BPMN 错误/升级以及审批 SLA 的正式数据均归入 ApprovaPlat 工作流业务表；完整菜单基线已包含 98 条目标记录，并吸收开发期增量和各审批能力权限。原 `.2` 的 Flowable `ACT_RE_MODEL` 版本唯一约束逻辑已重命名为 `8.0.0__workflow_model_version_guard.sql`，作为首个基线初始化门禁。数据库契约测试和发布门禁必须以当前正式基线重新执行；当前表数契约固定为总计 111、分项 `20/11/36/44`，三组只读验收共 58 项。

## CLAR-004 首个正式版本采用全新安装基线

- 状态：已确认
- 确认日期：2026-08-07
- 原始问题：首个正式版本是否需要兼容未正式发布的本地开发数据库，还是只建立全新安装基线？
- 正式结论：首个正式版本只支持全新安装。发布包必须包含完整 Flowable 官方表、完整 `wf_*` 业务表、完整菜单权限和模型版本唯一约束初始化；验收通过后，该版本成为不可修改的正式数据库基线。后续版本从该基线开始维护有序、可验证的增量迁移。
- 清理影响：删除未对外发布的 `.1`～`.14` 工作流业务升级脚本及菜单开发期增量，删除旧版五表安装说明、旧表数和仅面向本地历史结构的发布顺序；将模型版本唯一约束改为首个基线初始化步骤。
- 保持不变：首个基线的幂等性、只读验收、权限隔离、备份要求、数据库自动建表关闭和未来正式增量迁移的不可变约束。

## CLAR-005 文档按长期职责重建，不保留任务编号体系

- 状态：已确认
- 确认日期：2026-08-07
- 原始问题：`docs/workflow-production/01`～`08` 等文件来自历史任务阶段，后续开发持续修改这些任务输出，造成它们被误认为长期产品规范；应继续维护还是重建？
- 正式结论：不再维护按任务阶段编号的旧文档体系。只有能够长期约束架构、业务行为、数据库、部署发布和验收的内容才纳入 Git，并按职责重新分类、重新命名和基于当前代码重写。阶段计划、日期化状态、候选证据摘要和任务过程不作为正式项目文档。
- 新文档分类：`architecture` 记录稳定架构边界，`contracts` 记录业务行为，`database` 记录正式数据基线，`operations` 记录安装与发布规则，`testing` 记录验收契约；`docs/README.md` 是唯一索引。
- 清理影响：删除 `docs/workflow-production/`、根目录 `DEPLOYMENT.md` 和 `sql/flowable/README.md` 等旧输出；删除与审批平台无关的 Codex/OpenAI 协调器资料，以及已经由组件文档和正式业务契约覆盖的 BPMN 阶段台账。必要规则只在新文档中重新表述，不复制旧任务进度。同步清理 `.gitignore` 中阻止正式文档纳入版本控制的规则。
- 保持不变：代码、SQL、测试和发布门禁仍是可执行证据；文档与实现发生冲突时必须重新澄清并同步修正，不允许以“代码已经这样写了”自动覆盖正式业务结论。

## CLAR-006 BPMN 设计器以可安全执行能力为正式支持边界

- 状态：已确认
- 确认日期：2026-08-07
- 原始问题：BPMN 设计器应继续追求与参考设计器的功能数量对齐，还是只正式展示后端能够安全执行并完成验收的建模能力？
- 正式结论：只有后端能够安全解析、校验、部署、执行、持久化、审计并完成真实验收的建模能力，才允许标记为正式支持。不能因为前端能够绘制、导入或保存 XML，就把该能力描述为可执行业务功能。
- 产品表现：已支持能力可以正常建模和部署；仅支持 XML 往返或查看的能力必须明确标记为不可部署；完全未支持的能力不进入正式工具入口。
- 清理影响：不再维护与参考工程按数量对齐的 Phase 台账。缺失能力必须形成明确清单，由项目负责人决定排除、延后或另派独立任务实现。
- 保持不变：任何新增 BPMN 能力仍需同时完成前端编辑、后端白名单和语义校验、Flowable 真实执行、权限与审计、失败分支和自动化验收。

## CLAR-007 高价值 BPMN 能力必须通过独立任务补齐

- 状态：已确认
- 确认日期：2026-08-07
- 原始问题：标准循环、错误边界、升级边界、Participant、MessageFlow、多池协作及建模辅助元素中，哪些能力会直接影响审批平台的产品价值，哪些应排除或只保留标准 BPMN 表达？
- 正式结论：除已经明确不建议产品化实现的能力外，所有被确认具有真实审批业务价值但当前尚未形成完整闭环的能力，都必须通过独立任务完成，不允许继续以 Palette 可见、XML 往返或 Flowable 原生类型存在作为完成依据。
- P0-1：完整实现受控的重复审批与整改循环。标准循环必须达到优秀商业审批产品水平，至少覆盖可视化配置、循环进入和退出条件、最大次数、变量作用域、重复任务与表单回显、权限、并发、回滚、历史轨迹、审计和真实数据库验收；不得直接放开无边界的 `standardLoopCharacteristics` 表达式。
- P0-2：完整实现错误边界与升级边界。必须覆盖受控错误或升级的产生入口、编码目录、捕获范围、中断与非中断语义、外部连接器和服务任务联动、人工处理路径、权限、通知、失败零副作用、运行历史、审计以及真实数据库和浏览器验收；普通 Java 异常不得冒充 BPMN 业务错误。
- 独立任务：Participant、MessageFlow 与真实多池协作必须作为跨流程、跨参与方和跨系统编排能力单独设计与实现，不能把协作图形或 XML 连线描述为已经具备消息关联、可靠投递、幂等、权限、状态一致性和审计能力；具体优先级由 CLAR-008 确认为 P1。
- 保留但不强行赋予运行语义：Lane、Group、Annotation、Association 继续承担责任分区、分组和说明作用；ManualTask 遵循 Flowable 自动通过、不生成待办的标准语义，并通过名称和提示避免与 UserTask 混淆。如未来要求 Lane 自动分配权限或 ManualTask 形成可追踪人工办理，应分别作为新的业务能力重新澄清。
- 明确排除：ComplexGateway 不进入当前 Flowable 8 审批平台的实现任务；可以由排他、并行、包容和事件网关表达的业务路由不得引入自定义复杂网关执行器。其他仅为让图形元素看起来“可执行”而没有真实业务需求和完整闭环的扩展也不实施。

## CLAR-008 多池协作能力按 P1 排期

- 状态：已确认
- 确认日期：2026-08-07
- 原始问题：Participant、MessageFlow 与真实多池协作应与标准循环、错误和升级边界同列 P0，还是在两个 P0 核心能力稳定后按 P1 实施？
- 正式结论：Participant、MessageFlow 与真实多池协作定为 P1，必须通过独立任务完整实现，但交付顺序位于 P0 受控重复审批、P0 错误边界和升级边界之后。
- 完成标准：P1 不降低生产要求，仍须实现跨流程和跨系统消息关联、可靠投递、幂等、重试与死信、认证授权、事务和状态一致性、审计、可观测性、管理入口以及真实数据库、API 和浏览器验收；优先级只决定排期，不允许缩减业务闭环。

## CLAR-009 边界定时器与审批 SLA 纳入 P0 错误/升级边界

- 状态：已确认
- 确认日期：2026-08-07
- 原始问题：边界定时器、审批 SLA、超时提醒、自动催办和超时升级是否可以只依赖 BPMN timer XML 或 Flowable 原生 job，还是必须作为审批平台的错误/升级边界能力完整交付？
- 正式结论：边界定时器、审批 SLA、超时提醒、自动催办和超时升级纳入 P0-2 错误/升级边界任务。它们是审批业务的运行能力，不得以“支持 timer XML”“Flowable 已创建 job”或页面倒计时替代完整实现。
- 完成标准：必须基于真实异步执行器和正式持久化实现超时判定、业务日历、暂停/恢复、重复触发控制、权限隔离、通知投递、审计追踪、失败回滚和状态一致性；必须通过真实 MySQL、真实 API 和真实浏览器验收，并覆盖正常、并发、重试、通知失败、撤回/终止/挂起和恢复等分支。
- 排期关系：该能力与 P0-2 错误边界和升级边界同一交付门禁，优先于 CLAR-008 规定的 P1 Participant、MessageFlow 和多池协作；P1 的排期不降低其生产级完成标准。
- 保持不变：普通 Flowable timer 的 XML 解析、部署和引擎 job 运行只能作为底层机制复用；若缺少 SLA 规则、日历、权限、通知、审计或补偿闭环，只能标记为建模/引擎基础能力，不能称为审批 SLA 已实现。
