# 审批流程核心业务黑盒测试用例

设计日期：2026-09-06。适用项目：ApprovaPlat / RuoYi Flowable。当前状态：**用例已设计，全部未执行**。

本组包含 **56 条主用例**，覆盖申请、草稿、认领、审批、委派、转办、退回重提、会签或签、动态成员调整、撤回取消、终态控制、表单附件、权限及审计。参数化用例的每组输入必须分别执行、分别记录结果，56 条不等于 56 次请求。

## 1. 测试边界与判定方式

- 使用真实浏览器、不同账号会话及公开业务 API；通过详情、列表、流程图、意见记录、通知和下载结果判断行为。读取源码仅用于核对设计依据，执行用例不调用内部 Java 方法，不直接修改数据库或引擎状态来准备场景。
- 业务状态必须在页面刷新、重新登录后仍成立；成功提示、按钮消失或者单次接口成功不能单独作为通过依据。
- 每次失败后，都用新的查询核对原实例状态、任务归属、申请值、附件及成功操作记录。允许记录失败请求日志，但不得把失败动作展示为审批成功。
- 参数、身份、对象授权、状态冲突分别记录实际响应。HTTP 状态与响应体业务码分别保存，不把所有错误都要求为同一个状态码；下文明确指定的业务码和子码必须精确匹配。
- 浏览器能阻止的非法输入，再使用同一身份直接调用对应公开 API 验证后端拒绝；请求字段沿用浏览器真实请求结构，仅改变该用例所测字段。
- 本组验证核心功能及业务一致性；容量、长时间稳定性、灾难恢复、真实邮件投递、SLA、连接器、多池协作和复杂子流程完整验收另设专项。本组通过不能替代生产验收。

以下是本组测试需要通过正式设计、部署功能创建的夹具，不代表环境里已经存在。创建失败应记录环境阻塞，不能跳过前置条件后宣布用例通过。

| F2 候选认领 | A 发起 → 未指派的候选任务，候选为 B、C → 结束；分别准备候选用户、候选角色、候选部门三个变体 |

申请表配置：`title` 为必填文本、最长 20 个字符；`amount` 为必填数字；`expenseType` 为必选枚举 `TRAVEL/OFFICE`；`remark` 为可选文本；`attachments` 为附件字段。有效输入为 `title=差旅报销`、`amount=1000`、`expenseType=TRAVEL`、`remark=申请值-A`。测试长度使用普通汉字或 ASCII，不混入空白和代理对字符。

B 节点设置必填的 `reviewNoteB`，C 节点设置必填的 `reviewNoteC`。为字段权限测试另设只读字段及隐藏字段，记录其部署时权限与原始值。所有必需表单和权限配置须经正式部署校验。

附件使用无敏感信息的真实文件，准备允许类型、禁止类型、损坏或不存在的附件引用；记录当前单文件上限 L 和剩余配额 Q 的实际值及单位，边界文件按字节精确生成，不凭空假定系统限制。

### 2.3 通用执行约定

1. 每条用例、每个参数化子场景使用独立实例。需要“B 已通过”等状态时，实际登录 B 办理产生；不得手工改状态。
2. 成功动作后刷新当前账号和相关收件人列表，并重新获取详情；核对实例数量、活动任务集合、办理人、申请值及意见记录。
3. 失败动作前后保存上述可观察状态作比较；除独立并发成功请求产生的变化外，失败请求不得贡献额外业务变化。
4. 并发场景使用同步起跑的两个公开 API 请求，记录发送和返回时间。分别覆盖请求一先到、请求二先到及真正重叠；仅依次点击两个按钮不能证明并发正确性。
5. P0 表示流程错转、越权、重复处理或数据错误风险，作为核心业务验收阻断项；P1 表示应覆盖的常规回归。尚未执行、被环境阻塞、失败和通过必须分开统计。

## 11. 执行记录模板与通过标准

每条用例每个子场景一行，未执行时不得预填“通过”。建议复制本表到测试管理系统，证据文件存受控位置，不提交账号密码或 Token。
