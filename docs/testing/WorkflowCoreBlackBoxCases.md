# 长流程 UI 黑盒测试：照着页面操作即可

**状态：用例已设计，测试流程尚未搭建，测试尚未执行。**

本方案按真实用户的方式测试：登录、填写、选择、点击、等待，再检查页面上的结果。测试人员不需要读代码、查询数据库、调用接口或理解内部执行机制。

复用一条“综合采购审批”长流程，进行六组组合测试。流程管理员先准备好模型、账号及必要的外部测试环境；测试人员按以下步骤操作。

## 1. 先准备一条能在页面上找到的长流程

“综合采购审批”是本次要准备的测试模板名称，以下人员和选项也是测试数据，并非现有系统已经提供。管理员须先将它们配置好并发布。

**申请 → 普通初审 → 候选认领 → 会签一 → 会签二 → 或签 → 规则判断与条件分支 → 并行核验 → 子流程审批 → 预算确认 → 发送订单与等待回执 → 定时等待 → 归档结束。**

| 放在流程中的内容 | 测试人员怎样操作、怎样看结果 |
| --- | --- |
| 普通审批、候选认领、两组会签、或签 | 切换审批账号，在“待签”“待办”操作；查看谁收到任务、任务是否消失、是否进入下一节点 |
| 规则任务、条件分支、并行与包容网关 | 申请时改变金额、“跨境”“涉密”；查看走了哪条路径、哪些人收到任务，以及是否等齐应等待的人 |
| 展开子流程、调用活动 | 在子流程审批人的“待办”办理；在主流程详情查看关联流程、状态及表单显示的结果 |
| 事务、取消与补偿、错误与升级事件 | 使用管理员准备的正常/失败业务场景；查看是否进入“异常处理”“取消处理”等实际配置的支线。外部业务结果只能在对应系统的现有页面核对 |
| 服务任务、发送/接收任务、消息捕获/抛出 | 供应商账号在协作流程里办理确认；采购方刷新详情，检查等待是否解除。已有消息管理页用于查看投递结果 |
| 信号、定时器、事件网关、事件子流程、中断/非中断边界事件 | 按规定办理或暂不办理，等待提醒/超时；信号通过已配置流程动作触发；观察原任务是否保留，以及进入了哪条处理支线 |
| 普通开始/结束、终止结束 | 发起并走到对应结局；查看状态、结束时间和所有相关账号的剩余待办 |
| 池、泳道、消息流、连线、数据对象、数据存储、分组、注释 | 在设计器保存、关闭、重开及导入导出后查看，检查内容、布局及连接关系是否保留 |

准备账号：A 为发起人，B/C/D/E 为不同审批人，M 为管理员，V 为供应商，X 为与本次申请无关的普通用户。首次使用时，把字母替换成实际账号姓名。

关键配置：

- 首审为 B，候选复核为 C/D；会签一为 C/D/E，会签二为 B/E，或签为 C/D。
- 金额不超过 1000 走“小额审批”，超过 1000 走“大额审批”；跨境勾选税务复核，涉密勾选安全复核，两者都不选走默认路径；财务、法务两条并行核验必须都完成。
- 申请和不同审批节点设置名称明确的表单字段，准备一个附件；另设置只读、隐藏字段，便于从页面验证。
- 提醒和超时设成适合测试的短时间，由管理员告知实际时长。错误、升级、预算取消及不同结束方式，须有已配置的测试路径或现成业务操作入口。
- **退回在前面的人工审批段测试。** 不要求已调用外部服务、走过复杂子流程的申请仍能任意退回；后段是否提供入口按项目规则判断。

## 2. 六组测试

### U1：一路正常完成

数据：金额 999，跨境=是，涉密=否。

| 步骤 | 谁、在哪个页面、做什么 | 应该看到什么 |
| --- | --- | --- |
| 1 | A 打开“新建流程”，选择测试模板；先漏填一个必填项尝试提交，再补齐、上传附件并保存草稿 | 必填未填时有提示且不能正式提交；草稿列表能找到本次申请 |
| 2 | A 退出并重新登录，从草稿继续编辑，检查后提交 | 填写内容、附件仍在；“我的流程”只有本次一个申请；B 收到初审待办 |
| 3 | B 通过；C 在“待签”认领并办理；随后按会签一、会签二、或签顺序切换账号办理 | 认领后由认领人办理；会签最后一人完成前不进入下一步；或签一人通过后其他人的该任务失效 |
| 4 | 各分支及子流程审批人继续办理，V 在供应商流程确认订单；按配置等待定时节点，再完成收尾 | 小额分支、税务分支被执行；并行两路未完成前不进入下一步；子流程办完后主流程继续；正常消息到达后解除等待 |
| 5 | A 重新登录查看申请表单、历史表单、附件和“流转记录”；X 登录检查本人的列表，并尝试打开复制的申请页面地址 | 流程完成；各次意见与实际操作者一致，原申请与审批填写值不混淆；附件可正常打开；X 不能查看受限申请或下载其附件 |

### U2：更换人员，再退回修改

数据：第一次金额 999，退回后改为 1001；跨境=是，涉密=是。

| 步骤 | 谁、在哪个页面、做什么 | 应该看到什么 |
| --- | --- | --- |
| 1 | B 初审通过后，在候选人尚未处理时，从“已办”撤回，再重新办理 | 后继旧任务不能再办理；B 重新收到可办理任务；撤回和再次办理都有记录 |
| 2 | C 认领复核后点击“取消认领”；D 重新认领，委派 E；E 填意见点击“完成委派”；D 再转办 C，由 C 通过 | 取消认领后回到待签；委派办结后回 D，尚未进入下一节点；转办后由 C 办理，D 的旧页面不能再通过 |
| 3 | 会签一中 C 添加 B，再移除尚未完成的 E；B 通过，D 点击“退回” | 新增的人收到任务，被移除的人不能再办；退回后其余旧会签待办失效，A 只有一个待修改入口 |
| 4 | A 打开退回申请，修改金额和备注，点击“重新提交”；再次办理到或签，C 再退回，A 再次重提后走完全链 | 每次重提都从首审批继续；两组会签恢复各自正确人员，不能把不同组的人混用；后续走大额审批、税务和安全两条分支 |
| 5 | A 查看详情中的申请、历史表单和“流转记录” | 两轮修改及退回原因可区分；只完成原来的一个申请，没有重复创建流程 |

### U3：两个人同时操作，加上超时

数据：金额 1000，跨境=否，涉密=是。使用独立浏览器会话，避免两个账号互相覆盖登录。

| 步骤 | 谁、在哪个页面、做什么 | 应该看到什么 |
| --- | --- | --- |
| 1 | C、D 同时打开同一个“待签”任务，约定一起点击认领 | 最终只归一个人；另一人收到任务已被处理等提示；刷新后没有两个人同时持有同一认领任务 |
| 2 | 会签一中 D 打开“通过”弹窗并填写意见；C 先加签成功，再让 D 提交旧弹窗 | D 收到人员已变化等冲突提示；任务未直接完成；已填意见和表单保留；查看最新人员后，D 明确再次确认才继续 |
| 3 | 到或签时，C、D 都打开办理页面，约定同时点击通过，再分别刷新 | 流程只推进一次；其余或签任务失效；没有两个重复的下一节点任务 |
| 4 | 到提醒节点时暂不办理，收到提醒后仍等待到超时；事件网关选择让超时先发生，之后 V 再在页面完成迟到的确认 | 提醒发生时原待办仍在；中断超时后旧待办不能继续办；进入约定超时支线；迟到确认不把采购流程拉回已失效的正常分支 |
| 5 | 按已配置流程操作触发通知类事件子流程，完成其待办及主线 | 非中断事件子流程启动时主线仍在；相关任务完成后正确结束；金额 1000 走小额，包容分支只启动安全复核 |

此组只能证明本次页面操作下观察到的竞争结果；两次点击若实际先后完成，不据此宣称已证明所有并发情况。

### U4：服务失败、异常处理和补偿

本组需要管理员提前准备能从正常业务页面触发的失败场景，以及可以查看结果的外部测试系统。

| 步骤 | 谁、在哪个页面、做什么 | 应该看到什么 |
| --- | --- | --- |
| 1 | A 发起“外部处理失败”场景，金额 1001，跨境和涉密都不选；审批人正常办理 | 走大额、默认分支；处理失败时不能显示整个申请已成功完成 |
| 2 | 在外部系统现有页面修正业务条件；若消息管理页面提供且允许“重试”，由 M 点击，再刷新申请详情 | 失败情况可查看；恢复后仅推进一次，不能出现重复业务结果。不能把消息管理的“重试”当作所有服务任务都有的按钮 |
| 3 | 分别办理准备好的错误和升级业务条件，按页面出现的处理待办继续 | 进入对应的异常/升级处理节点；原任务保留或取消符合已配置规则，不出现相互矛盾的两个办理入口 |
| 4 | 对预算已预占的申请，通过准备好的业务选择分别测试事务取消和显式补偿；在预算系统页面查看结果 | 进入正确处理支线；如果预算页面可查，应看到对应预占被释放且没有重复释放；无法从任何页面查看的结果标记“UI 无法验证” |

“事务取消”和“显式补偿”使用两个独立申请。没有页面触发条件或结果入口时，该部分记为“缺少测试条件”，不能要求测试人员改代码或调用接口补做。

### U5：中途结束，旧页面不能再办

同一流程分别发起四个独立申请，不能在已取消的申请上继续测试驳回。

| 子场景 | 谁、在哪个页面、做什么 | 应该看到什么 |
| --- | --- | --- |
| 驳回 | 财务、法务并行核验尚未全部完成时，一个当前办理人点击“驳回”并填原因 | 状态为已驳回；其余相关待办消失；另一人已打开的旧办理页面不能再通过 |
| 取消 | 流程等待回执时，A 从“我的流程”取消本人申请并填原因 | 状态为已取消；原申请没有可继续办理入口；迟到回执不能恢复它 |
| 管理员终止 | 被调用子流程仍有待办时，M 从流程管理页面终止申请 | 主子流程按项目规则结束；原审批人刷新或提交旧页面，均不能再完成旧任务 |
| 模型中的终止结束 | 通过管理员准备的业务选项走“终止结束”路径，同时保留一个应被该路径结束的活动 | 该终止节点应结束的相关任务消失；不把“到达一个结束节点”误判为所有任务已结束 |

完成后重新登录查看状态、结束时间及原因。供应商的独立流程需要按图中设置的取消通知或超时路径自行结束，不能假定采购方一结束它就自动结束。

### U6：从设计器验证全部节点

| 步骤 | 谁、在哪个页面、做什么 | 应该看到什么 |
| --- | --- | --- |
| 1 | M 或设计者打开综合模型，逐段查看节点、属性、子流程、池、泳道、连线、数据对象和注释；保存后关闭重开 | 内容与连接关系保留，展开/折叠不会改变流程含义 |
| 2 | 在设计器导出，再通过页面导入到测试副本；查看并校验 | 节点、事件配置、表单、人员、消息关系及子流程引用不丢失 |
| 3 | 在独立测试副本中加入复杂网关或标准循环，再从页面尝试部署 | 可保存和往返的内容保留；部署明确提示不支持，不能假装发布成功 |
| 4 | 通过页面导入管理员提供的脚本任务、手工任务测试文件 | 项目禁止的模型被明确拒绝；不要求测试人员编辑 XML；手工任务也不应有可用的新增/转换入口 |
| 5 | 查看“更改元素”菜单中的普通任务、临时子流程、条件/链接事件及其他事件变体，与管理员提供的节点清单逐项核对 | 每项记录为可运行、明确不支持或待确认。可画出来不等于已验证可运行；尚无业务规则或 UI 操作路径的项不能填通过 |

## 3. 哪些地方不能靠“点一下”凭空测出来

- 当前“运行事件审计”页面用于查询消息和信号记录，没有通用的“发送事件”测试按钮。
- 消息、信号、服务和补偿仍在本轮范围内，但必须由准备好的协作流程、外部系统页面或业务条件触发。定时节点通过实际等待触发。
- 缺触发条件记“缺少测试条件”；页面没有结果展示记“UI 无法验证”。由流程准备人员补齐可操作条件后再测，不把只画出节点算作测试通过。
- 本方案保持“全部节点”的目标，不把尚不能用 UI 操作验证的部分悄悄删掉，也不宣称已完成全节点验证。
